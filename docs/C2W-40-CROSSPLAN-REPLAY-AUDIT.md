## Newly proved defects and specific repairs

### C2W-01 — Idempotency reuse across cases/templates (File 17/19, CF02-FR-009/032)
**Before:** `OperationsRepository::enqueueDelivery()` accepted an existing outbox Idempotency Key whenever payload hash, recipient and channel matched, even with **different case UUID or notification template**. It could return the prior notification's ID, thus losing the intended case/template message without emitting the correct work item.

**Fixed:** Existing receipt replay now requires exact equality of all five elements: payload hash, recipient, channel, **case UUID**, and **template key**; otherwise a bounded collision error. Legitimate exact replay is still accepted with no new DB writes. Test `tests/c2w-40-notification-replay-boundaries.php`: **32 change-mask vectors** across five binding dimensions plus **8 legitimate exact replays** = **40/40** PHP mock scenarios.

**Residual:** Actual File 17/19 provider and outbox delivery, production concurrency and signing/translation consent need staged validation. The shared platform File 19 must remain canonical notification owner.

### C2W-02 — Legal Hold replay silently ignores review deadline (CF02-FR-031/034)
**Before:** `OperationsRepository::applyHold()` and `::applyCategoryHold()` checked prior Case/Category, reason and authority but not **review_due_at**. Reusing the same Idempotency Key with a different legal review date returned an old hold while disregarding the changed date.

**Fixed:** Both methods now bind replay to exact original UTC-microsecond `review_due_at` too; the same request can replay, while a changed review deadline fails closed. Test `tests/c2w-40-legal-hold-deadline-replay.php`: **20 date offsets for case holds + 20 for category holds** = **40/40** PHP mock scenarios.

**Residual:** Real WordPress/MariaDB/transaction/concurrent hold-vs-purge integrity, lawful retention schedules, manual hold review and category-owner acceptance remain untested externally.

### C2W-03 — Time-dependent receipt payload prevented exact intake replay (CF02-FR-002/003/032)
**Symptom:** The exact WordPress/MariaDB Active Runtime Integration workflow failed at the original `tests/wordpress-runtime-smoke.php` replay check: `Exact intake replay was not idempotent.`. This was not declared a random CI flake.

**Root cause proven from source:** `ComprehensiveRestController::createCase()` rebuilt receipt `received_at` with `$this->now()->format(DATE_ATOM)` during *every* request. A replay crossing a wall-clock second regenerated a different payload hash, so the idempotent `enqueueDelivery` correctly refused to replay the existing outbox item. This discrepancy was pre-existing and surfaced clearly in the real-runtime integration test.

**Fix:** build receipt timestamp from the immutable canonical Case `created_at`, normalized UTC using `DateTimeImmutable`. Both initial attempt and later exact replay now generate the same receipt payload. The WordPress/MariaDB smoke explicitly sleeps two seconds before replay to enforce the timestamp boundary, and rejects changed-body key reuse.

**Proof:** at source commit `dcc89dd6c3d17d43e6d9745281e20c2531b6cce4`, all **5/5 workflows success**, including **Active Runtime Integration with actual ephemeral WordPress and MariaDB**; PHP 8.1–8.4 succeed. This is controlled CI-environment evidence, **not** production WordPress or Hostinger acceptance.
