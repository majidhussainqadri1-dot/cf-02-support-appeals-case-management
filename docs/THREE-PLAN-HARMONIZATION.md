# CF-02 Three-Plan Harmonization — C2-K

## Governing baseline

This corrective batch reconciles three sources without allowing any one implementation document to silently erase another:

1. Sabri Social Homeopathy Platform — Definitive Master Plan v3.0.
2. Consolidated All-Chats Recovered Directive Register v2.1, including `CHAT-BIZ-022`, `CHAT-GOV-023` and `CHAT-QA-001`.
3. CF-02 — Support, Appeals and Case Management plan v1.0, requirements `CF02-FR-001` through `CF02-FR-034`.

The later Founder-approved directive register controls where it expressly changes an earlier business, visual or governance rule. CF-02 remains an orchestrator for support and appeals; it does not become the native authority for identity, moderation, ranking, finance, clinical care, security incidents or privacy-right decisions.

## Corrected implementation invariants

### Free service and non-privilege

- The active category is `learning_access`; the old `learning_billing` key is accepted only as a migration alias.
- Donation, sponsorship, paid promotion, payment tier and Founder favoritism are prohibited support-priority, SLA, assignment, review, appeal or quality signals.
- No requester can self-assign P1/P2 authority. Requester impact and urgency are bounded inputs; authoritative severity remains staff/native-policy controlled.
- A future financial contract remains conditional and can only receive an authorized request/status projection.

### Institutional due process

- Good-faith inquiry and disputed interpretation cannot themselves trigger discipline.
- A serious alleged violation requires written notice, policy version, allegations, evidence references, a response opportunity, conflict-free reviewer, proportionality assessment, appeal route and native-owner reference.
- CF-02 coordinates the dossier and appeal. The responsible canonical owner executes any access, role, contract or institutional action.
- A disciplinary case cannot close until required native-owner implementation evidence is recorded.

### Privacy-safe File 26 projection

- File 26 receives only a versioned, thresholded aggregate of final, implemented appeal outcomes.
- Pending, reopened or unimplemented outcomes are excluded.
- Raw case IDs, people, text, notes, messages, attachments, evidence, contact data, donation and payment facts are forbidden.
- Appeal use never creates an adverse ranking penalty. Cohorts below the privacy threshold are suppressed.

### Canonical category routing

- Category normalization happens before persistence or routing.
- Each active category resolves through `SupportTaxonomy` to exactly one configured queue.
- Provider adapters cannot select or widen a queue independently of the canonical taxonomy.

### Frontend, RTL and accessibility

- Requester CSS and JavaScript are packaged files, not inline runtime templates.
- All visible script strings are supplied through the WordPress text domain.
- The component uses the platform green token with a safe fallback, CSS logical properties, 44px minimum controls, keyboard tab behavior, focus visibility, reduced-motion and forced-color handling.
- Network failures expose translated, accessible status and trace information rather than silent or raw failures.
- File 20 remains the application-shell owner and File 25 remains the component/visual-contract owner.

## Truthful status

The source can be called a three-plan harmonized **coded candidate** only after exact-head CI and deterministic package evidence pass. It is not Hostinger-staging accepted, live deployed or operational. Real companion/provider contracts, security deployment tests, browsers/devices, accessibility, load/soak, migration, restore, rollback, staffing, observation and Founder exact-artifact acceptance remain separate gates.
